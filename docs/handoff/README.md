# NearSoul: пакет документов для команды

Состояние на 2026-10-18, коммит `9945ca1` и новее. Живой тестовый стенд: https://nearsoul-alpha-y6qr.onrender.com

| № | Документ | Для кого | Что отвечает |
|---|---|---|---|
| 1 | [PRD (продукт, as-built)](01-PRD.md) | менеджер, дизайнер, агент | Что за продукт, для кого, какие функции, правила, монетизация, что готово |
| 2 | [Technical Design](02-technical-design.md) | разработчик, агент, техлид | Архитектура, модули, потоки данных, решения и почему |
| 3 | [Technical Specification](03-technical-specification.md) | разработчик, агент, QA | Точные контракты: API, база данных, формулы движка, лимиты, переменные окружения, тесты |
| 4 | [Production Readiness](04-production-readiness.md) | менеджер, основатель, DevOps | Что обязательно сделать и настроить перед настоящим запуском, с аккаунтами и чек-листом |

## Как этим пользоваться

**Менеджеру:** читать 1 → 4. Документ 1 описывает продукт и статус, документ 4 даёт список работ, денег и аккаунтов до запуска.

**Агенту (Claude Code или другому):** читать все четыре, затем `CLAUDE.md` в корне. Порядок приоритета источников при противоречии:
1. Прямое указание основателя в чате.
2. `docs/prd-change-requests.md` (принятые изменения CR-1…CR-29).
3. `docs/prd/` (исходный PRD v3.1, только для чтения).
4. Эти handoff-документы (сводка «как построено»; если они расходятся с кодом, прав код + тесты, а документ надо обновить).

**Правила для агента, которые нельзя нарушать** (подробно в документе 3, §12):
- Soul Engine остаётся чистым детерминированным TypeScript без I/O, покрытие ≥ 95 %.
- ИИ пишет только текст. Он никогда не меняет баллы, фильтры или доступ.
- Никогда не отдавать точную локацию, ответы на вопросы, сырые баллы, содержимое Soul Talk и тексты сообщений (API, логи, аналитика).
- Платный контент проверяется только на сервере. Чат и безопасность никогда не за пейволлом.
- Тестовые функции альфы (демо-профили, симулятор локации, бесплатная активация уровней, коды на экране) невозможны в production.
- Не переписывать PRD. Изменения оформлять как CR в `docs/prd-change-requests.md`.
- После каждого шага: lint → typecheck → tests → build, затем запись в `docs/implementation-status.md`.
- Никогда не запускать `prisma migrate diff --shadow-database-url` с рабочей базой (это стирает её).
- Не запускать `dart format` на целых файлах (переформатирует весь файл).
